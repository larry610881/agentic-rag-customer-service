## 三、要跟 GX10 保管單位問的五個問題

速度差異幾乎完全由第 2 題決定，其餘是配套確認。

| # | 問題 | 為什麼要問 |
|---|---|---|
| 1 | 確切型號與晶片（例如 GB10／GB200／其他） | 決定後續所有推算的基準 |
| 2 | **記憶體頻寬是多少 GB/s？** | **產字速度幾乎與頻寬成正比，這題最關鍵** |
| 3 | 記憶體容量與型態（GDDR / HBM / LPDDR 統一記憶體） | 決定能不能同時常駐兩個模型；統一記憶體通常頻寬較低 |
| 4 | 是否支援 FP4／NVFP4 原生運算 | 支援的話可用 4-bit 版本，速度約可翻倍 |
| 5 | 能否安裝 ollama 或 vLLM 並對外開一個 HTTP 埠 | 決定能不能直接跑我們現成的量測腳本 |

## 四、拿到頻寬數字後，怎麼估

產字（decode）是**記憶體頻寬受限**：每產一個字，要把該次用到的權重讀過一遍。

| 模型 | 每 token 讀取量 |
|---|---|
| 35B-A3B q8_0（MoE，35B 參數但每次只啟用 3B） | 約 **3.3 GB** |
| 35B-A3B nvfp4（4-bit） | 約 **1.7 GB** |
| 27B q8_0（dense，全參數） | 約 **30 GB** |
| 27B nvfp4（4-bit） | 約 **15 GB** |

**估算方式**（以 35B-A3B q8_0 為例）：

```
GX10 產字速度 ≈ 112 字元/秒 × (GX10 頻寬 ÷ 1,800 GB/s)
GX10 總時間   ≈ 首字時間 + 174 字元 ÷ GX10 產字速度
```

首字（prefill）偏算力而非頻寬，受影響較小，可暫以 1.5–3 秒估。

**對照表（填入頻寬即可讀）**

| GX10 頻寬 | 35B-A3B q8_0 產字 | 35B-A3B q8_0 總時間 | 27B q8_0 總時間 |
|---|---|---|---|
| 1,800 GB/s（＝測試機） | 112 字元/秒 | 2.2 秒 | 5.5 秒 |
| 900 GB/s | 約 56 字元/秒 | 約 4.6 秒 | 約 11 秒 |
| 500 GB/s | 約 31 字元/秒 | 約 7.6 秒 | 約 20 秒 |
| 273 GB/s | 約 17 字元/秒 | 約 12 秒 | 約 36 秒 |

> 4-bit（nvfp4）版本可將產字速度約提升一倍，總時間對應縮短。

## 五、兩個結論不受硬體影響

1. **MoE 必選，dense 不可行。** 每 token 讀取量差約 9 倍（3.3 GB vs 30 GB），設備頻寬越低差距越大。測試機上 27B 已是 35B-A3B 的 2.5 倍慢，換到低頻寬設備會拉開到接近 9 倍。
2. **答題品質、工具呼叫、結構化輸出三項與硬體無關。** 那是模型本身的能力，換機器不變。本次評測的這三項結論可直接沿用。

## 六、最快的定案方式

不必等規格推算——**直接量**。整套量測工具已完備，在 GX10 上只需：

```bash
ollama pull qwen3.6:35b-a3b-q8_0     # 38.7 GB
ollama pull qwen3.6:35b-a3b-nvfp4    # 23.6 GB（若支援 FP4）
# 起 ollama 服務並對外開一個 HTTP 埠（預設 11434）
```

之後在平台後台把供應商的 `base_url` 指到該位址，跑同一份 92 題題組，即可得到
「雲端 / 租用測試機 / GX10」三方對照。**半天可完成，無額外成本，不需修改任何程式。**
